# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- `.github/workflows/test.yml`: a CI test matrix for every pull request and push to `main`. On GitHub-hosted runners: `windows-latest` runs the Pester unit suite (`tests/run-tests.ps1`) under pwsh 7 and under Windows PowerShell 5.1 (the host the login task and an elevated `install.ps1` use), plus a third job with `-IncludeIntegration` (safe there, since the runner VM is thrown away; non-blocking until two failing integration tests are fixed); `ubuntu-latest` and `macos-latest` run the bats suites and the pytest suite in `tests/shared/`, with macOS using the system `/bin/bash` 3.2. A `ps-lint` job runs the shared `J-MaFf/.github` PSScriptAnalyzer workflow on the self-hosted runner, skipped for pull requests from forks so fork code never reaches that machine. Each job is capped at 20 minutes. Covers the Pester workflow #221 asked for ([#227](https://github.com/J-MaFf/gitconfig/issues/227)).
- `install.ps1` STEP 6 (and the login auto-update) now show an animated `| / - \` spinner while `pip install` runs: `Install-PythonDeps` routes installs through a new dependency-free `Invoke-PipInstall` helper that runs pip in a background job and animates the wait in the foreground, so a cold install of rich/textual no longer looks hung. Without a real console (CI, redirected output, the non-interactive login task — detected via `Test-ConsoleSpinnerSupport`) it degrades to a single plain status line routed through the existing `-Logger`, emitting no control characters; the final `[OK]`/`[WARN]` summary lines are unchanged ([#210](https://github.com/J-MaFf/gitconfig/issues/210)).
- `git issues` alias: lists the current repo's open GitHub issues as a rich table (number, title, labels, updated age) via `gh issue list --json`. `--all`/`-a` goes account-wide — every repo owned by the authenticated user via `gh search issues` (adds a repo column, works from any directory); `--all --local` restricts the scan to git repos in immediate subdirectories of the derived Scripts root (the parent of this repo), skipping non-GitHub repos with a note. Filters: `--mine`/`-m` (assigned to you) and `--label <name>`/`-l <name>`; `--web`/`-w` opens the browser instead of a table ([#211](https://github.com/J-MaFf/gitconfig/issues/211)).
- `git skill diff` subcommand: prints the full diff of drifted skill(s) in `~/.claude/skills` (all of them, or one by name via `git skill diff <name>`), so you can review exactly what changed before running `git skill publish`. Drifted skills are discovered by parsing `skill-audit`'s existing report rather than reimplementing its classification logic; no network fetch is made (diff is a local comparison) ([#208](https://github.com/J-MaFf/gitconfig/issues/208)).
- Adopted **beads (`bd`)** as the Dolt-backed task/memory layer beneath GitHub Issues ([#152](https://github.com/J-MaFf/gitconfig/issues/152)). The bead graph syncs via `refs/dolt/data` on `origin`; `.beads/config.yaml` and `.beads/metadata.json` are tracked while the JSONL exports and embedded Dolt DB are gitignored (dolt-only sync).
- `install.ps1` now checks for a working Python interpreter up front (via the existing `Resolve-Python`), right after admin elevation and before any file is touched. Python only powers the `git alias` browser (`rich`/`textual`); the core gitconfig install works without it, so a missing interpreter now warns once and asks `Continue anyway? (y/n)` instead of surfacing as three scattered warnings deep into the run — `-Force` auto-continues past the prompt, consistent with what `-Force` already means everywhere else in the script ([#219](https://github.com/J-MaFf/gitconfig/issues/219), [#220](https://github.com/J-MaFf/gitconfig/pull/220)).

### Changed
- macOS and Linux now share one implementation of `install.sh`, `cleanup-gitconfig.sh` and `initialize-local-config.sh` in `scripts/unix/`, which detects the OS ([#229](https://github.com/J-MaFf/gitconfig/issues/229)). The per-OS pieces live in a new `scripts/shared/platform.sh`: the auto-sync scheduler (`scheduler_install`/`scheduler_remove`/`scheduler_status`, with a launchd backend on macOS and a cron backend on Linux; a systemd user timer is [#246](https://github.com/J-MaFf/gitconfig/issues/246)), the HTTPS credential helper (osxkeychain on macOS; gh, then libsecret, on Linux) and the signing detection. `scripts/mac version/*.sh` and `scripts/linux version/*.sh` stay as thin wrappers, so existing commands, docs and already-installed launchd plists and cron lines keep working. Run directly, the `scripts/unix/` scripts have no wrong-platform guard to trip; the wrappers keep theirs. Deliberate behaviour changes:
  - **Linux signing matches macOS** (finding 28). When git already has a `user.signingkey` (the template ships one with `commit.gpgsign = true`) and there's no key file or op-ssh-sign, `initialize-local-config.sh` now writes `gpg.ssh.allowedSignersFile`, so `git log --show-signature` verifies. Linux also gains the `~/.ssh/claude_desktop` key candidate, the `~/.ssh/git-sign-no-agent` wrapper, and 1Password's `/opt/1Password/op-ssh-sign`. An on-disk key now needs its `.pub` next to it on Linux too (that file feeds `allowed_signers`); without one, the key is ignored, as on macOS.
  - **macOS also finds op-ssh-sign in the 1Password app bundle** (`/Applications/1Password.app/Contents/MacOS/op-ssh-sign`), after the two Homebrew paths.
  - **The auto-sync job runs `scripts/shared/update-gitconfig.sh`** directly (with the repo path, as before) instead of the per-OS wrapper. Cron stays daily at 9 AM with output in `/tmp/gitconfig-update.log`; launchd stays at login.
  - **Cron lines are tagged `# gitconfig-autoupdate`.** Install and cleanup find our line by that marker, plus any untagged line from an older install that runs an `update-gitconfig.sh`, so re-installing migrates an old line instead of adding a second one, and other cron entries are never touched.
  - **The Linux installer now checks its cron job in STEP 7 and prints the closing error summary**, as macOS did. Linux cleanup now runs under `set -e` like macOS, and both cleanups print the same messages.
  - **`--no-scheduler`** skips the auto-sync job on either OS; `--no-launchd` and `--no-cron` are accepted on both as synonyms.
  - The wrong-platform error now suggests `scripts/unix/<script>`. Headers name the OS on both platforms (`GitConfig Setup (Linux)`, `# Machine-Specific Git Configuration (Linux)`), and the Linux config writes `signingkey` in lowercase (git treats key names case-insensitively).

### Fixed
- `tests/run-tests.ps1` exited 0 however many tests failed when run without `-PassThru` (its normal use): `Invoke-Pester -Configuration` returns a result object only when `Run.PassThru` is set, and that was tied to the script's own `-PassThru` switch, so `$results` was `$null`. It now always requests the result, and also fails when Pester returns nothing or reports a failed container (a test file whose setup throws). New `tests/TestTooling.Tests.ps1` pins the exit codes ([#227](https://github.com/J-MaFf/gitconfig/issues/227)).
- `config/pester.config.ps1` pointed code coverage at `./scripts/install.ps1` and `./scripts/Cleanup-GitConfig.ps1`, which moved to `scripts/windows version/`, and ran only 3 of the test files, including the machine-changing `Integration.Tests.ps1`. It now runs all of `tests/` with the Integration tag excluded, covers the whole `scripts/windows version/` folder, and builds its paths from its own location so it works from any directory ([#227](https://github.com/J-MaFf/gitconfig/issues/227)).
- Installing again no longer loses your original files ([#226](https://github.com/J-MaFf/gitconfig/issues/226)). The installers ran a full cleanup (STEP 0) on every run, which moved your files to a single `Existing.<file>.bak` slot, so the second run overwrote the backup of the first. Windows also deleted existing files with no backup before linking.
  - Every platform now saves backups as `<file>.bak.YYYYMMDD-HHMMSS`, keeping the newest 5 per file. `GITCONFIG_BACKUP_KEEP` changes the limit and `0` keeps all. Older `*.bak` files are never touched.
  - A symlink that already points into the repo is skipped when it's correct and removed without a backup when it's stale, so re-running doesn't create new backups.
  - Cleanup now runs only with `install.sh --reinstall` or `install.ps1 -Reinstall`. As a side effect, `install.ps1 -NoTask` without `-Reinstall` no longer deletes an existing login task.
  - `Initialize-Symlinks.ps1` backs up an existing file before replacing it with a link.
  - `initialize-local-config.sh --force` and `Initialize-LocalConfig.ps1 -Force` back up the old `~/.gitconfig.local` before overwriting it.
- `install.sh`/`install.ps1` STEP 4 (`git config --global core.excludesfile`) was removed. `~/.gitconfig.local` already sets it. Writing it into `~/.gitconfig` made that file differ from the template, so every login sync regenerated it. Before `~/.gitconfig` is regenerated, the scripts now list the names (not the values) of any settings the template would drop, and suggest moving them to `~/.gitconfig.local`. The README now says to put your own settings there ([#226](https://github.com/J-MaFf/gitconfig/issues/226)).
- `Cleanup-GitConfig.ps1 -KeepLocal` ignored `-KeepLocal` when it relaunched itself elevated, so the elevated run deleted `~/.gitconfig.local` anyway. The relaunch now passes the flag on ([#226](https://github.com/J-MaFf/gitconfig/issues/226)).
- The login/daily auto-sync could fail to run at all, on every platform ([#225](https://github.com/J-MaFf/gitconfig/issues/225)):
  - **Repo path.** `update-gitconfig.sh` and `Update-GitConfig.ps1` defaulted to `~/Documents/Scripts/gitconfig`, so a clone anywhere else synced nothing. They now default to the repo they live in, and the cron entry, the Windows task and the `git selfupdate` alias pass the path explicitly. The path is checked before the `docs/` log dir is created: the old order ran `mkdir -p <path>/docs` first, so a wrong path was silently created and "passed" the check. A missing path now prints an error to stderr and exits 1.
  - **Windows execution policy.** The scheduled task and `git selfupdate` ran `powershell -File` without `-ExecutionPolicy Bypass`, so on a Restricted client the script never started. Both now use `-NoProfile -NonInteractive -ExecutionPolicy Bypass`.
  - **Task settings.** `Register-LoginTask.ps1` now triggers at the installing user's logon (not any user's), one minute late, needs a network, and stops after 10 minutes instead of the 72-hour default. A task left by an older install (different path or arguments) is replaced instead of reported as already existing. `Initialize-Symlinks.ps1` now calls `Register-LoginTask.ps1` instead of keeping its own copy of the registration code.
  - **`set -e` aborts.** `((X++))` returns status 1 when `X` is 0, so `set -e` ended the Linux and macOS install/cleanup scripts at the first counter increment (mac cleanup died right after removing the launchd plist). Every counter now uses `X=$((X+1))`.
  - **Missing `crontab`.** The Linux installer and cleanup no longer abort when `crontab` isn't installed; they skip the cron step with a warning.
  - **launchd PATH.** The launchd plist now sets `PATH` (Homebrew first), so `git` and `python3` from Homebrew are found at login.
  - **Hangs.** The updaters set `GIT_TERMINAL_PROMPT=0`, so a missing credential fails the pull instead of waiting on a prompt nobody can see.
  - **Branch switching.** On a branch other than main, the updaters no longer run `git checkout main`, which switched the user's work-in-progress branch out from under them at login. They leave the branch checked out and fast-forward main in place with `git fetch origin main:main`. A diverged main is logged as a warning.
- Branch pruning could delete live branches and lose unmerged work ([#228](https://github.com/J-MaFf/gitconfig/issues/228)):
  - `git cleanup`, `git main` and both login-time updaters (`update-gitconfig.sh`, `Update-GitConfig.ps1`) found "gone" branches by text-matching `git branch -vv`, whose lines include each branch's last commit subject. A subject containing `: gone]` got a live branch force-deleted, and the helper read any branch tracking a remote other than `origin` (a fork's `upstream`) as local-only, so `git cleanup --force` deleted it. All four now read `git for-each-ref` fields (`%(upstream:track)`, `%(worktreepath)`), keeping the skip for branches checked out in another worktree.
  - Every deletion used `git branch -D`. Each now tries `-d` first and falls back to `-D` only for a branch whose remote is gone (squash-merged PR branches). Each deleted tip SHA is printed (or logged by the updaters) with the command to restore it.
  - `git cleanup --force` deletes local-only branches with `-d` only; unmerged ones are kept and listed.
  - `git start` created branches tracking `origin/<default>`, so the first `git push` failed under `push.default=simple` and cleanup never saw the branch as gone. It now uses `git switch --no-track`. A branch made earlier can be fixed with `git branch --unset-upstream`.
  - The default branch came from `init.defaultBranch` (the name for *new* repos), so `git main` and `git cleanup` used `main` in a repo whose remote default is `master`. They now read `origin/HEAD`, falling back to `init.defaultBranch` and then `main`.
  - `git main` pulled twice (once without `--ff-only`, so a diverged main got a merge commit). It now fetches once and fast-forwards only: a diverged branch is reported with its ahead count, never merged. Conflicts are detected with `git diff --name-only --diff-filter=U` instead of searching `git status` text for `UU`/`AA`/`DD`, which also matched file names.
  - Exit codes are now meaningful:
    - `git cleanup` always exited 0. It now exits 1 when the fetch, a deletion or the switch back fails, and `git main` fails when its cleanup does.
    - The bash updater ended with `exit $?` (the status of the log redirect). The Windows updater had no final `exit`. Both now exit 1 when `~/.gitconfig` can't be converged or a branch can't be deleted. An offline fetch or pull stays a warning.
    - An unknown helper subcommand now prints to stderr and exits 2.
    - `git issues` rejects unknown flags (exit 2) instead of ignoring a typo like `--lable`.
- `generate_gitconfig` (mac/Linux) mangled a repo or home path containing `&`: under bash 5.2+ `patsub_replacement`, the unquoted replacement in `${c//\{\{REPO_PATH\}\}/$repo_root}` treats `&` as "the matched text", so a repo at `/a&b` rendered as `/a{{REPO_PATH}}b`. The replacement is now quoted (and the assignment left unquoted, since bash <= 4.2 keeps inner quotes literally inside a double-quoted expansion); a bats test reproduces `/a&b` ([#236](https://github.com/J-MaFf/gitconfig/issues/236)).
- Stale docs: `docs/WORKFLOW.md` named the Windows task "Update Git Config", a `pull-daily.log` file and `scripts\Update-GitConfig.ps1`; it now uses the real task name (`GitConfig Pull at Login`), log (`docs\update-gitconfig.log`), log format and `scripts\windows version\` paths. The root README's cleanup line had the same wrong task name. `scripts/linux version/README.md` no longer claims the scripts need bash 4 associative arrays (they use none; only the optional bash Ctrl-G widget needs bash 4). `Cleanup-GitConfig.ps1 -Help` no longer lists a "Clears git SSH signing config" step the script never performed, and now describes its actual steps; Pester tests run `-Help` to pin both ([#236](https://github.com/J-MaFf/gitconfig/issues/236)).
- `git main` / `git cleanup` printed `Warning: Failed to delete branch '+': error: branch '+' not found` once per merged branch still checked out in a linked worktree. `git branch -vv` marks those with a leading `+` (like `*` for the current branch), and the parser took the first field — `+` — as the branch name. Such branches are now skipped (git refuses to delete them until the worktree is removed) and listed by name with a hint to remove the worktree. The same fix applies to the login auto-update prune in `scripts/shared/update-gitconfig.sh` and `scripts/windows version/Update-GitConfig.ps1`, which now log a "Skipped" line instead of a failed delete ([#223](https://github.com/J-MaFf/gitconfig/issues/223)).
- `Initialize-Symlinks.ps1`'s STEP 2 self-test ran `git alias` before `install.ps1` STEP 6 installs its `rich` dependency, so it always printed `[WARN] git alias command failed` on a fresh Python install — even on runs that went on to succeed, since STEP 7 re-runs the identical, correctly-ordered check later in the same run. The premature self-test is removed; STEP 7 remains the sole `git alias` verification ([#219](https://github.com/J-MaFf/gitconfig/issues/219), [#220](https://github.com/J-MaFf/gitconfig/pull/220)).
- `git skill status` (and `git skill sync`, which shares the renderer) could print `[OK] Nothing to publish from this machine` while `~/.claude/skills` had an uncommitted working tree — and `git update` was skipping the repo as `Skipped (dirty)` at the same time. The state block reported only what `skill-audit` sees, and `skill-audit` classifies *skill directories*; changes to anything else in the repo (`.claude-plugin/`, `scripts/`, top-level docs, a directory rename) were invisible, so the scheduled sync could stop fast-forwarding with no visible signal. `_render_skill_state` now also runs a repo-wide `git status --porcelain` on the skills repo (`_repo_dirt_paths`), filters out paths under skill folders so the audit's own drifted/untracked counts aren't double-reported, lists up to 5 of the remainder, and names the consequence (`Blocks the sync - git update skips this repo as dirty`). When dirt is present the all-clear line is scoped to `[OK] No skill changes to publish` so it can't be misread as a clean tree ([#217](https://github.com/J-MaFf/gitconfig/issues/217)).
- `Integration.Tests.ps1`'s "should be valid Python" check invoked bare `python -m py_compile`, bypassing the repo's own `py` -> `python3` -> `python` resolution rule — on a launcher-only machine this hit the WindowsApps stub (exit 9009, errors swallowed) and failed spuriously for a helper script that was actually valid. Now resolves the same way `gitconfig_helper.Tests.ps1` does, skipping gracefully if no interpreter exists at all; a new `Tag 'Unit'` static check catches a regression without needing `-IncludeIntegration` ([#202](https://github.com/J-MaFf/gitconfig/issues/202), [#206](https://github.com/J-MaFf/gitconfig/pull/206)).
- `Update-GitConfig.Tests.ps1`'s "valid PowerShell script" assertion wrapped `PSParser::Tokenize` in `Should -Not -Throw`, but `Tokenize` never throws on syntax errors (it reports them via a discarded `[ref]` parameter) — an unparseable script would still pass. Replaced with `Language.Parser::ParseFile` + a captured error-count assertion, the pattern already used elsewhere in the suite ([#201](https://github.com/J-MaFf/gitconfig/issues/201), [#205](https://github.com/J-MaFf/gitconfig/pull/205)).
- `install.ps1` STEP 7 re-resolved Python with a standalone first-hit `Get-Command py/python3/python` chain instead of reusing `Resolve-Python` (already dot-sourced for STEP 6's `Install-PythonDeps`). `Get-Command`'s first hit can be a 0-byte WindowsApps stub that `Resolve-Python` treats specially, so a stub found first could make STEP 7 print a spurious `[WARN] Python 'rich' not importable` right after STEP 6 succeeded via the correctly resolved interpreter. STEP 7 now reuses `Resolve-Python` ([#200](https://github.com/J-MaFf/gitconfig/issues/200), [#204](https://github.com/J-MaFf/gitconfig/pull/204)).
- `Resolve-Python` skipped every 0-byte WindowsApps app-execution-alias stub outright, so a machine whose only Python is the Microsoft Store package (no python.org/PyManager launcher) could never resolve an interpreter at all. Now that the probe passes a non-empty `-c` argument (see #197/#198 below), probing a stub is safe — it prints a message and exits 9009, no UI. Stubs are now set aside and probed *last*, after every real candidate and launcher fallback, so a real interpreter never loses to a stub found earlier on PATH but a Store-only install can still resolve. This also surfaced that invoking a genuinely broken candidate can *throw* rather than just exit non-zero (impossible to hit before, since stubs were never probed) — the probe is now wrapped in try/catch so any candidate failure degrades to "try the next one" instead of crashing `Resolve-Python`'s best-effort caller chain ([#199](https://github.com/J-MaFf/gitconfig/issues/199), [#203](https://github.com/J-MaFf/gitconfig/pull/203)).
- The Windows login task *still* logged "No Python interpreter found" after #161: `Resolve-Python` probed candidates with `& $cand -c ''`, and Windows PowerShell 5.1 (the task host) silently drops empty-string arguments to native commands — the probe ran `py -c` (exit 2) and rejected every candidate, including #161's working launcher fallbacks. pwsh 7 passes the empty arg correctly, so the probe always looked fine interactively and #161's "aliases only resolve in interactive sessions" diagnosis missed the real failure. The probe is now `-c 'pass'`, and a new `tests/Functions.Tests.ps1` pins it: a fake-candidate behavioral test that rejects a missing `-c` argument catches the old probe under both 5.1 and pwsh 7 ([#198](https://github.com/J-MaFf/gitconfig/pull/198)).
- `file_owner_uid` returned filesystem-stat garbage on Linux: it tried the BSD `stat -f %u` form first, but on GNU/Linux `-f` means `--file-system`, so `stat -f %u PATH` dumps a filesystem-info block to stdout before failing on the `%u` specifier — the `||` then appended the real uid, yielding `<block>\n<uid>`. The mac production caller is `uname`-guarded to macOS so real runs were unaffected, but the mac/functions bats suites (run cross-OS via `GITCONFIG_ALLOW_CROSS_OS=1`) failed 2 tests on Linux. Reordered to try GNU `-c` first — it fails cleanly on macOS (no stdout), so BSD `-f` still covers that host, and the non-zero exit for a missing path is preserved. Shared suite now 44/44 on Linux ([#196](https://github.com/J-MaFf/gitconfig/pull/196)).
- Dead mid-test `! grep` assertions in the shared bats suites were silently swallowed: bats exempts a `!`-negated command from its errexit/ERR-trap machinery, so only a *terminal* negation fails the test — the mid-test `! grep` checks in `mac-initialize-local-config.bats` (and one in `functions.bats`) never asserted anything, and the rest passed only by accident of placement. Converted all 13 negated-grep assertions across `functions.bats`, `mac-` and `linux-initialize-local-config.bats` to `run ! grep` (position-independent, bats >= 1.5) and added a `bats_require_minimum_version 1.5.0` pragma to each ([#194](https://github.com/J-MaFf/gitconfig/pull/194)).
- `git skill publish` on Windows died on `publish-skill.ps1`'s `#Requires -Version 7`: the dispatcher (`_run_skill_script` in `gitconfig_helper.py`) launched every wrapper script with Windows PowerShell 5.1, which refuses to start PS7-only scripts even when pwsh 7 is installed. It now resolves `pwsh` first, falls back to `powershell` only for the WinPS-compatible sync/status wrappers, and prints an actionable install hint when a PS7-only script is dispatched without pwsh on PATH ([#189](https://github.com/J-MaFf/gitconfig/pull/189))
- The Windows-generated `~/.gitconfig.local` now sets `core.longpaths = true`: Dolt's git-remote-cache (behind beads' `bd dolt push`) nests refs past Windows MAX_PATH, and stock Git for Windows fails with "Filename too long". The setting had been hand-applied to the global config on 2026-07-02, but template regeneration (`git selfupdate`) rewrites `~/.gitconfig` and silently wiped it — it regressed unnoticed until 2026-07-08. It now lives in the never-clobbered local config (Windows-specific, so the shared template stays platform-neutral), with a Pester regression guard ([#187](https://github.com/J-MaFf/gitconfig/pull/187))
- Running the wrong platform's `install.sh` displaced the machine's correct `~/.gitconfig.local`: STEP 0 (`cleanup-gitconfig.sh --force`) moved it to a backup before the platform guard inside `initialize-local-config.sh` (STEP 3) could fire, leaving the install aborted mid-run. Both `install.sh` wrappers now carry the same `uname -s` guard (with the `GITCONFIG_ALLOW_CROSS_OS=1` escape hatch) before any destructive step, with a `tests/shared/install-platform-guard.bats` suite pinning it ([#185](https://github.com/J-MaFf/gitconfig/pull/185)).
- The mac `initialize-local-config.sh` credential block now emits the empty `helper =` reset line before `osxkeychain`, matching the Linux blocks from #180: `credential.helper` is multi-valued and accumulates across config levels, so a stale helper inherited from a migrated other-platform `~/.gitconfig.local` would otherwise answer first ([#184](https://github.com/J-MaFf/gitconfig/pull/184)).
- The generated `~/.gitconfig.local` on Linux carried no HTTPS credential helper — and the Ubuntu server's was a macOS-flavored file applying `credential.helper = osxkeychain`, which broke every HTTPS git operation (`bd dolt push`, private-repo pulls: "git: 'credential-osxkeychain' is not a git command"). The Linux initialize script now emits a platform-appropriate `[credential]` block (gh CLI helper scoped to github.com/gist.github.com with an empty reset line so stale inherited helpers can't answer first, libsecret fallback, commented hint otherwise), and both the mac and linux `initialize-local-config.sh` refuse to run on the wrong OS (`GITCONFIG_ALLOW_CROSS_OS=1` escape hatch for the sandboxed bats suites) ([#180](https://github.com/J-MaFf/gitconfig/pull/180)).
- The Windows `Initialize-LocalConfig.ps1` config-verification test failed when the suite ran on macOS: the script builds `USERPROFILE`-relative paths with backslashes, so on Unix hosts verification read a mixed-separator path and warned spuriously. The test now skips on non-Windows hosts (discovery-safe check that still runs under Windows PowerShell 5.1), making the suite fully green on macOS ([#178](https://github.com/J-MaFf/gitconfig/pull/178)).
- `tests/gitconfig_helper.Tests.ps1` hardcoded `python` (28 failures on macOS, where the interpreter is `python3`) and built git fixtures from the Windows-only `$env:TEMP` with unguarded `Push-Location`/`Pop-Location` — on macOS a failed fixture setup let the tests' git commands run against the developer's checkout (committing fixture data and renaming the checked-out branch to `main`). The interpreter now resolves `py` → `python3` → `python` (whole file skips cleanly when absent), fixtures use the cross-platform temp root with `-ErrorAction Stop`, and location pops are guarded ([#177](https://github.com/J-MaFf/gitconfig/pull/177)).
- The shared beads Dolt DB (schema v32) was unusable from bd 1.1.0 clones, and the upstream migration chain is broken for this lineage (migration 0047 references a `wisps` table that never existed). Re-initialized the graph fresh on the native schema — the old graph was verified empty at every version — and replaced `refs/dolt/data` on origin. Other machines must upgrade `bd` and re-run `bd bootstrap` ([#175](https://github.com/J-MaFf/gitconfig/pull/175)).
- Regenerating `~/.gitconfig.local` on a shared Mac wiped the hand-added `safe.directory = /opt/homebrew` entry, so git's dubious-ownership check broke `brew update`. The mac initialize script now emits the entry whenever the Homebrew repo exists and is owned by a different user ([#170](https://github.com/J-MaFf/gitconfig/pull/170)).
- Regenerating `~/.gitconfig.local` on the Mac reverted commit signing to the template's agent-based 1Password key (Touch ID prompt per commit; hangs unattended runs). The mac initialize script now detects an on-disk signing key (`~/.ssh/claude_desktop` or `~/.ssh/id_ed25519_signing`) and emits the file-based signing block — including the `git-sign-no-agent` wrapper when present — preferring it over `op-ssh-sign` ([#173](https://github.com/J-MaFf/gitconfig/pull/173)).
- Windows login scheduled task logged "No Python interpreter found" even when Python was installed: `Resolve-Python` picked the 0-byte WindowsApps app-execution-alias stub, which only resolves in an interactive session. It now skips those stubs and falls back to the real PyManager/launcher path ([#161](https://github.com/J-MaFf/gitconfig/pull/161)).
- Non-ASCII em-dashes (U+2014) in `Update-GitConfig.ps1` and `gitconfig_helper.py` failed the ASCII Encoding tests (Windows PowerShell 5.1 compatibility) ([#164](https://github.com/J-MaFf/gitconfig/pull/164)).
- The Pester suite mutated the real machine (overwrote `~/.gitconfig`/`~/.gitconfig.local`, toggled the login scheduled task): `run-tests.ps1` set tag filters under the wrong Pester config section so `-ExcludeTag Integration` was ignored, and two test files generated config against the real `$env:USERPROFILE`. Tests now sandbox HOME and integration tests are excluded by default ([#167](https://github.com/J-MaFf/gitconfig/pull/167)).

### Changed
- Trimmed `.gitignore_global` to editor/OS junk, `__pycache__/` and secrets. It applies to every repo on the machine, yet it ignored lockfiles (`package-lock.json`, `yarn.lock`, `Gemfile.lock`, `*.lock`), `lib/`, `bin/`, `build/`, `dist/`, `vendor/`, `*.bat`, `*.cmd`, `*.exe`, `*.com`, `*.jar`, `.vscode/` (which this repo tracks), `.vimrc` and `*.vim`, so new files of those kinds were silently never committed; it also repeated many patterns. Language and build patterns belong in each project's own `.gitignore`. This repo's `.gitignore` now lists `.beads.gate.lock`, which only the old global `*.lock` was hiding. A new `tests/shared/gitignore-global.bats` checks what is and isn't ignored and that no pattern is duplicated ([#236](https://github.com/J-MaFf/gitconfig/issues/236)).
- `claude.yml` now calls the shared reusable Claude workflow in [J-MaFf/.github](https://github.com/J-MaFf/.github) instead of carrying its own copy ([#215](https://github.com/J-MaFf/gitconfig/pull/215))
- `git main --all` now scans the derived Scripts root (the parent of the repo containing `gitconfig_helper.py` — `~/Documents/Scripts` on a standard install) instead of the current working directory, sharing one repo-discovery helper with `git issues --all --local`; the dirty-repo triage, per-repo headers, summary table, and exit codes are unchanged ([#211](https://github.com/J-MaFf/gitconfig/issues/211)).
- `git skill sync` / `git skill status` now render in Python with rich instead of dumping the wrapper scripts' raw text ([#191](https://github.com/J-MaFf/gitconfig/pull/191)). The old output replayed the last *scheduled* sync's log tail — including its stale `[drift]` flag and the CLAUDE.md `1 file(s) copied.` noise — next to freshly computed state, which read as a contradiction, and printed identical before/after blocks around the pull. The new view keeps only what stays true from the log (last run's stamp + pull result), computes drift once and live via `skill-audit` (still the single source of truth), colors the counts (green aligned / yellow drift / red problems), warns when the repo isn't on `main`, and turns the gone-upstream pull failure into an actionable "switch back to main" hint. The claude-skills wrappers remain for direct use and as the automatic fallback if the rich view fails.
- `install.ps1` no longer overwrites an existing `~/.gitconfig.local` (create-if-missing). The machine-specific config is preserved on re-install; regenerate deliberately with `Initialize-LocalConfig.ps1 -Force` ([#166](https://github.com/J-MaFf/gitconfig/pull/166)).
- `tests/run-tests.ps1` excludes integration tests by default; opt in with `-IncludeIntegration` (run only on a real machine or VM) ([#167](https://github.com/J-MaFf/gitconfig/pull/167)).
